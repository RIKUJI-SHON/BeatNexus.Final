# 広告配信システム 改訂要件定義書: 契約広告 最小配信モード (2025-08-21)
作成者: GitHub Copilot  
参照: `docs/BeatNexus.md`, 旧版: `docs/広告配信システム_要件定義_2025-08-20.md`

## 0. 改訂背景 / Pivot
初期ドラフトではインプレッション / クリック計測・トークン署名・重み付き選択・日次集計を含むフル MVP を想定していた。現時点の事業要件は「契約した広告を確実に所定の枠へ表示し掲載価値を提供する」ことが最優先となり、計測 (impression / click) と最適化アルゴリズムは後段フェーズへ延期する。よって以下の最小配信モードへ要件を再定義する。

## 1. 目的 (Goal)
契約/合意済みの広告クリエイティブをアプリ内の定義済み Placement に表示できる最小機能を短期実装。計測停止下でもフロント表示を安定させ、後日の計測・最適化再導入時に最小差分で拡張可能な構造を保つ。

## 2. スコープ (In Scope)
- 既存スキーマ(advertisers, ad_campaigns, ad_creatives, ad_placements, ad_flights) の再利用
- 単一配信 API (`/ad/serve`) の再実装 (最小ロジック)
- Placement 毎の表示対象 Creative を運営が制御できる仕組み（暫定: 優先度付きマッピングテーブル or 直接クエリ規約）
- フロント `AdSlot` による遅延ロード & レイアウト安定
- 計測無効化状態 (impression/click 送信なし)

## 3. 非スコープ (Out of Scope / Deferred)
- impression / click 計測保存 (ad_events への書込み) 再稼働
- JWS トークン署名・検証
- デイリーキャップ / imp_goal の強制
- 重み付きランダム選択 / A/B 最適化
- 集計マテビュー / ダッシュボード
- 不正検知 / 高度ターゲティング

## 5. ユースケース (Revised)
1. 運営が広告主・キャンペーン・クリエイティブを登録
2. Placement と紐付け (最小: マッピングテーブル or flight 経由で指定)
3. Edge `/ad/serve` に対しフロント `AdSlot` から placement_key を送信
4. API が当該 placement に現在有効な 1 件の creative を返却
5. クリエイティブが表示され契約要件 (掲載期間 / 露出位置) を満たす

## 7. データモデル (再利用 + 追加提案)
既存テーブルは変更しない。計測停止中でも ad_events は保持（将来再利用）。

### 7.1 追加提案テーブル (任意 / オプション)
`ad_placement_creative_map` (最小制御用)
```sql
create table if not exists ad_placement_creative_map (
  placement_id uuid references ad_placements(id) on delete cascade,
  creative_id uuid references ad_creatives(id) on delete cascade,
  priority int default 100,
  is_active boolean default true,
  pinned boolean default false,
  updated_at timestamptz default now(),
  primary key (placement_id, creative_id)
);
create index if not exists ad_pcm_active_priority_idx on ad_placement_creative_map(placement_id, is_active, priority);
```
利用方針: pinned=true があれば最優先1件。無ければ priority ASC で最初の1件。空なら fallback → NoFill / HouseAd。

（オプション: 既存 `ad_flights` を流用し placement & campaign 両面管理する場合は当テーブルを省略してもよい。簡潔さ優先のため本改訂では map テーブル採用を推奨。）

## 8. 配信アルゴリズム (最小)
入力: placement_key
手順:
1. placement_id 解決 & is_active
2. `ad_placement_creative_map` から pinned=true AND is_active を探し 1 件 (priority ASC)。
3. 見つからなければ pinned=false, is_active=true を priority ASC limit 1。
4. 取得できなければ `{ ok:false, code:'AD_NO_FILL' }`。
5. 取得できたらクリエイティブ基本フィールドを JSON 返却。token は null。

## 9. API 仕様 (改訂)
| Method | Path | Body | 戻り値 | 備考 |
|--------|------|------|--------|------|
| POST | /ad/serve | `{ placement: string }` | `{ ok:true, data:{ placement_key, creative:{creative_id,headline,body,cta_text,target_url,file_url?}, token:null } }` | 200 |
| POST | /ad/serve | 無効 placement | `{ ok:false, code:'AD_INVALID_PLACEMENT' }` | 400 |
| POST | /ad/serve | No mapping | `{ ok:false, code:'AD_NO_FILL' }` | 200 |

認証: public (Supabase Edge Function) / RLS は参照のみ許容ビュー利用可。

## 10. フロント要件
- `AdSlot`: 現行実装を利用。`STATIC_AD_OVERRIDES` は段階的廃止予定 (mapping 再開後削除)。
- token が null の場合、impression / click フックは送信スキップ。
- HouseAd は NoFill / 開発時検証用途。

## 11. 運用インターフェース (暫定)
最小段階: SQL / Supabase ダッシュボードで `ad_placement_creative_map` を直接編集。
将来: 管理 UI ページ (フィルタ + 並び替え + ドラッグ優先度変更)。

## 12. セキュリティ / RLS
`ad_placement_creative_map`: internal_admin, ad_ops 以外書込み禁止。select は viewer まで許可。end_user は直接参照不要 (Edge 経由のみ)。
Edge Function でのみ内部クエリを実行し JSON を返却。直接 creative テーブルの余計な列は露出しない。

## 13. 非機能要件 (改訂最小)
| 項目 | 指標 |
|------|------|
| レイテンシ | p95 < 150ms (シンプル1クエリ) |
| 可用性 | Supabase Edge 基準 (標準) |
| キャッシュ | 初期は無し (必要なら CDN / 60s) |
| 安定性 | クリエイティブ切替反映 < 1 分 (TTL 無しなら即時) |

## 14. 将来拡張復帰ポイント
| 項目 | 復帰条件 | 追加作業 |

## 16. マイグレーション方針
1. create table `ad_placement_creative_map`
2. RLS (select: all logged roles, modify: internal_admin, ad_ops)
3. シード: 既存 placements に対し 1 つダミー creative を割当
4. Edge Function デプロイ → フロント fetch テスト

## 17. テスト観点 (最小)
| 観点 | 期待 |
|------|------|
| 無効 placement | AD_INVALID_PLACEMENT |
| mapping 無し | AD_NO_FILL 応答 / fallback 表示 |
| pinned 優先 | pinned=true が常に返る |
| priority | pinned 無し時 priority ASC | 
| レイテンシ | p95 <150ms (手動計測) |

## 18. リスク & 緩和
| リスク | 内容 | 緩和 |
|--------|------|------|
| 計測不在の透明性 | 広告主へレポート不能 | 契約書面で「掲載保証のみ」を明示 |
| 手動更新ミス | 間違った creative 割当 | pinned/priority UI 将来導入 | 
| 将来拡張時の再設計 | map テーブルが冗長化 | flights ベースにマージ可能なシンプル構造保持 |
