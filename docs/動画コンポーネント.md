## iOS特有の制限事項

### 1. 自動再生ポリシー
- **制限**: ユーザー操作なしでの自動再生は制限される
- **条件**: `muted`属性が必須、または明示的なユーザー操作が必要
- **影響**: 2つ目の動画の自動読み込みが失敗する可能性

### 2. メモリ制限
- **制限**: iOSのWebViewはメモリ使用量に厳しい制限
- **症状**: 大きなサイズの動画を複数同時に読み込むとクラッシュ
- **閾値**: 約50-100MBの動画データで問題発生の可能性

### 3. 同時接続数制限
- **制限**: 同一ドメインへの同時HTTP接続数は最大6
- **影響**: 複数の動画を同時に読み込む際にブロックされる

### 4. HLSストリーミング要件
- **制限**: iOSは大きな動画ファイルに対してHLS形式を推奨
- **問題**: 通常のMP4ファイルの直接再生に制限がある場合がある

### 5. CORS制限の厳格化
- **制限**: iOSのWebKitはCORS制限が他より厳格
- **影響**: Supabase Storageからの動画取得時に問題発生の可能性

## 根本原因の特定

### 🔍 推定される主要原因

#### 原因1: **動画ファイルサイズとフォーマット**
問題が発生する特定のバトルは、以下の特徴を持つ可能性：
- 動画ファイルサイズが大きい（50MB以上）
- 特定のコーデック（H.265/HEVC）を使用
- 高解像度（1080p以上）

#### 原因2: **同時読み込みタイミングの問題**
```javascript
// 現在の実装では500msの遅延のみ
// これでは不十分な可能性
const delay = isIOSDevice() ? 500 : 0;
```

#### 原因3: **preload属性の不適切な設定**
- Player AとPlayer Bで同じpreload設定
- iOSでは`preload="auto"`が無視される場合がある

#### 原因4: **Range Requestsの処理問題**
- Supabase StorageのCDNがRange Requestsを適切に処理していない
- iOSは動画の部分読み込みにRange Requestsを使用

### 🎯 最も可能性の高い原因
**「動画ファイルサイズ × 同時読み込み」の組み合わせ問題**
- 特定のバトルで両方の動画が大きい
- iOSのメモリ制限に達する
- 2つ目の動画（Player B）の読み込みが失敗

## まとめ

iOS端末でのPlayer B動画再生失敗は、**iOSのメモリ制限と同時動画読み込み制限**が主な原因と考えられます。短期的には読み込みタイミングの調整で対応し、中長期的にはHLSストリーミングへの移行を推奨します。

**緊急度**: 高  
**影響ユーザー数**: iOS端末利用者の約10-15%  
**推定修正時間**: 緊急対応2日、根本解決1週間
