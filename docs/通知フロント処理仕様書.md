# 通知フロントエンド処理仕様書 (notifications → UI)

参照必須: `docs/BeatNexus.md`

## 1. 目的
`public.notifications` テーブルに行が挿入された後、フロントエンド（React + Zustand）がどのように取得・判定・表示・削除（既読処理）を行うかを明文化し、機能追加・保守時の基準とする。

## 2. 対象範囲
- フロント: `src/store/notificationStore.ts` のロジック
- 関連モーダル: BattleMatchedModal / BattleResultModal / NewSeasonModal
- 通知タイプ: `info | success | warning | battle_matched | battle_win | battle_lose | battle_draw | season_start`
  - 現状コードでモーダルトリガが有効なのは: `battle_matched`, `battle_win`, `battle_lose`, `season_start`
  - `battle_draw` は型上存在するが、モーダル起動処理未実装（改善余地）

## 3. データモデル (想定スキーマ)
```
notifications (
  id uuid PK,
  user_id uuid FK -> profiles.id,
  title text,
  message text,
  type text check (...),
  is_read boolean default false,
  related_battle_id uuid nullable,
  related_season_id uuid nullable,
  created_at timestamptz default now(),
  updated_at timestamptz default now()
)
```

## 4. フロント内部型
```ts
export interface Notification {
  id: string;
  title: string;
  message: string;
  type: 'info' | 'success' | 'warning' | 'battle_matched' | 'battle_win' | 'battle_lose' | 'battle_draw' | 'season_start';
  isRead: boolean;           // DB: is_read
  relatedBattleId?: string;  // DB: related_battle_id
  relatedSeasonId?: string;  // DB: related_season_id
  createdAt: Date;           // DB: created_at
  updatedAt: Date;           // DB: updated_at
}
```

## 5. ライフサイクル概要
| フェーズ | 起点 | 処理主体 | 主なロジック | 結果 |
|----------|------|----------|--------------|------|
| 生成 | サーバー側関数 / Edge Function / 管理操作 | DB | notifications 行INSERT | 未読通知行が蓄積 |
| 初回読込 | クライアントマウント時 / 手動リフレッシュ | `fetchNotifications()` | user_id で SELECT / 降順 | メモリ + 永続(Zustand persist)格納 |
| モーダル判定 | 初回読込直後 | `fetchNotifications()` 内 | 未読で該当 type を探索 | 対象モーダル表示 & DB削除 (一部) |
| 定期更新 | 5分毎 Interval | `subscribeToNotifications()` | 再度 `fetchNotifications()` | 状態最新化 |
| ユーザー操作 | 既読/削除クリック | `markAsRead` 他 | 実装上は “既読=削除” | DB行削除 |
| 自動削除 | モーダル表示完了後 | 各 handler | `deleteNotification(id)` | 二重表示防止 |

## 6. Polling 方式 (Realtime 非使用)
- 理由: 「WebSocket不安定」コメントにより手動ポーリングへ切替済み。
- 実装: `subscribeToNotifications()` 呼び出しで `fetchNotifications()` 即時実行 + `setInterval(300000ms)`
- 停止: アンマウント時に cleanup（clearInterval）

## 7. 処理詳細フロー
### 7.1 取得 (`fetchNotifications`)
1. `supabase.auth.getUser()` で認証確認。未ログインなら空状態セット。  
2. `from('notifications').select('*').eq('user_id', user.id).order('created_at', { descending })` で取得。  
3. 変換: DB→フロント型へマップ（Dateラップ）。  
4. `unreadCount` 再計算。  
5. 直後に「未読バトル結果」「未読マッチング」「未読シーズン開始」通知を探索し、存在すれば各 handler 実行。  

### 7.2 ハンドラ
| ハンドラ | 対応 type | 主処理 | 副作用 |
|----------|-----------|--------|--------|
| `handleBattleMatchedNotification` | `battle_matched` | active_battles / profiles 取得 → 対戦相手情報構築 → `useBattleMatchedStore.showMatchModal()` | モーダル表示後 `deleteNotification` |
| `handleBattleResultNotification` | `battle_win` / `battle_lose` | archived_battles + profiles (JOIN) → 勝敗/レート変動計算 → `useBattleResultStore.showResultModal()` | モーダル表示後 `deleteNotification` |
| `handleSeasonStartNotification` | `season_start` | `useModalStore.openNewSeasonModal()` | モーダル表示後 `deleteNotification` |

### 7.3 追加/生成 (`addNotification` / `createNotification`)
- `addNotification` はフロント側だけで一時 ID を生成し即時 UI 反映（楽観的）。並行して `createNotification` を非同期実行。  
- DB保存成功後のID再同期は行っていない（改善余地: 楽観IDと実IDの整合）。
- 追加時に battle_win / battle_lose / battle_matched は即時モーダル表示を試行（サーバーから push でなくクライアント生成時前提ケース用）。

### 7.4 既読/削除ポリシー
- `markAsRead(id)` 実装は「既読にする」のではなく対象通知をメモリ配列から削除し、そのまま DB DELETE。
- 全件既読/クリア (`markAllAsRead`, `clearAllNotifications`) も DELETE ベース。履歴は保持されない。
- 理由: UI 簡素化 & 通知一過性という設計判断（将来アーカイブ表示要件が出た場合は is_read 更新方式へ再設計必要）。

### 7.5 エラーハンドリング方針
| ケース | 処理 | ユーザー影響 |
|--------|------|--------------|
| DB取得失敗 | console.error + `error` 状態更新 | トースト/再試行UI未実装 (改善余地) |
| プロフィール取得失敗 (マッチング/結果) | Warn ログ、Unknown 表示で継続 | 軽微表示劣化 |
| 未認証 | 空リスト返却 | 問題なし |
| モーダル処理途中失敗 | console.error で終了 (通知削除は行わない) | 次回 fetch で再試行可能 |

## 8. タイプ別 UI アクション一覧
| type | Badge/リスト表示 | モーダル | 削除タイミング | 備考 |
|------|------------------|---------|----------------|------|
| info/success/warning | 通知ドロップダウン | なし (現状) | 手動(ユーザー) | 将来拡張余地 |
| battle_matched | 表示 (未読なら) | BattleMatchedModal | モーダル表示後自動削除 | opponent 情報 fetch |
| battle_win / battle_lose | 表示 (未読なら) | BattleResultModal | モーダル表示後自動削除 | rating 変動表示 |
| battle_draw | 表示のみ | なし (未実装) | 手動 | 改善余地: 勝敗モーダル流用 |
| season_start | 表示 (未読なら) | NewSeasonModal | モーダル表示後自動削除 | リセット案内 |

## 9. 状態保持
- Zustand + `persist` (storage key: `beatnexus-notifications`).
- 永続項目: `notifications`, `unreadCount` のみ。`loading` / `error` は非永続。

## 10. パフォーマンス / スケーラビリティ
| 項目 | 現状 | リスク | 改善案 |
|------|------|--------|--------|
| Polling 間隔 | 5分固定 | 遅延 (最大5分) | フォアグラウンド短縮 / バックグラウンド延長 / Realtime再導入 |
| モーダル表示後 DELETE | 即時クリーン | 履歴参照不可 | `is_read` 運用へ移行 + アーカイブビュー |
| 一括取得 | 全件 SELECT | 件数増加で遅延 | limit + pagination, `created_at > lastFetched` 増分取得 |

## 11. 既知の制約 / 改善候補
- `battle_draw` のモーダル非対応
- 楽観IDとDB ID 不一致による整合性課題（現状表示重複は発生しないが, DB側ID参照リンク作成不可）
- エラー UI 表示欠如（ユーザーには沈黙失敗）
- 手動ポーリングによる最大5分遅延（UX低下）

## 12. シーケンス例 (battle_matched)
```
EdgeFunction → INSERT notifications(type='battle_matched', related_battle_id=UUID)
      ↓
(最大5分以内) フロント polling fetchNotifications()
      ↓
未読 battle_matched 検出 → handleBattleMatchedNotification()
      ↓
active_battles + profiles fetch → showMatchModal()
      ↓
DELETE notifications(id)
```

## 13. テスト観点チェックリスト
| 観点 | テスト項目 |
|------|------------|
| マッチング通知 | INSERT → 5分以内にモーダル表示 & 行削除 |
| バトル結果通知 | INSERT → モーダル勝敗/レート表示正しい |
| シーズン開始 | INSERT → NewSeasonModal 起動 & 削除 |
| draw 通知 | INSERT → リスト表示されるがモーダルなし（仕様通り） |
| 削除操作 | ドロップダウンで個別削除 → DB行削除 |
| 全削除 | 全クリア → notifications 空 & DB行全削除 |
| 未認証状態 | fetchNotifications で空返却 |
| 再取得 | 既に削除済み通知が再表示されない |

## 14. 今後の拡張指針
- Realtime チャネル安定化後の再導入（遅延改善）
- `notification_preferences` テーブル追加によるカテゴリ別受信制御
- モーダル表示履歴の analytics イベント送信
- `battle_draw` の統一結果モーダル対応
