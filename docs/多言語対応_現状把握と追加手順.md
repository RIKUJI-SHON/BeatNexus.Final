# BeatNexus 多言語対応: 現状把握と追加手順

作成日: 2025-08-09
作成者: GitHub Copilot
関連: docs/BeatNexus.md, docs/新規アカウント作成システム仕様書.md

---

## 目的
- 現在の言語設定の実装（フロント/DB）を俯瞰し、追加言語を安全に増やすための標準手順を定義する。
- 実装時の変更ポイントとマイグレーションの雛形を提示する。

## 現状の仕組み（コード/DB）

### フロントエンド
- i18n初期化: `src/i18n/index.ts`
  - i18next + `i18next-browser-languagedetector` を利用。
  - `resources`: en/ja をロード。
  - `supportedLngs: ['en','ja']`
  - `fallbackLng: 'en'`
  - `detection.convertDetectedLanguage`: 現状は "ja* は ja、それ以外は en" に強制マッピング。
    - 追加言語を導入しても、この関数が 'en' へ潰してしまうため要修正。

- 言語検出ユーティリティ: `src/lib/utils.ts`
  - `detectBrowserLanguage()`
    - `supportedLanguages = ['ja','en']` 固定。
    - 未対応は 'en' にフォールバック。
  - `validateLanguageCode(language)`
    - `supportedLanguages = ['ja','en']` 固定。
    - 未対応は 'ja' にフォールバック（detect と不一致）。
    - フォールバック整合性のため 'en' に寄せることを推奨。

- 初期化フック: `src/hooks/useLanguageInitialization.ts`
  - ログイン済み: DB `profiles.language` を取得→i18n変更。
  - 未ログイン: `detectBrowserLanguage()` 結果を採用。
  - 取得失敗時はブラウザ言語へフォールバック。

- サインアップ時メタデータ: `src/store/authStore.ts`
  - `supabase.auth.signUp({... options.data: { language: detectBrowserLanguage() }})`
  - 新規作成時、DBトリガーがメタデータを参照できる前提。

### データベース（Supabase/Postgres）
- プロフィール言語: `profiles.language`
  - `docs/BeatNexus.md` では `language varchar CHECK (language IN ('en','ja'))`（デフォルト記載なし）。
  - 過去マイグレーション `20250720120000_fix_new_user_language_initialization.sql` では DEFAULT 'ja' 設定・メタ言語反映の実装あり。
  - 後続 `20250726000004_security_production_ready.sql` の `handle_new_user()` は言語設定ロジック未実装（かつ `email` カラム参照あり）。
  - `20250727120000_remove_profiles_email_phone_columns.sql` で `profiles.email` を削除。以降の `handle_new_user()` は別マイグレーションで修復済みであるべき（レポジトリ内に代替版の明示ファイルが見当たらないため、現行本番と差異がある可能性あり）。

- トリガー: `on_auth_user_created`（`auth.users` AFTER INSERT → `public.handle_new_user()`）
  - 新規ユーザー作成時に `profiles` を自動作成。
  - 言語設定は「メタデータの `language` を安全にホワイトリスト適用して保存」するのが設計方針。

> 注意: リポジトリの履歴上、`handle_new_user()` の実装は変更が続いており、一部に不整合が残っている形跡があります。追加言語導入前に、関数が "emailカラム非依存" かつ "言語設定を扱う" 最新版へ統一されていることを確認してください。

## 追加言語設計ポリシー
- 言語コードは i18next の一般的な運用に合わせて基本は2文字（例: 'ko', 'es', 'fr', 'de', 'zh'）。リージョンが必要な場合のみ 'pt-BR' のように付与。
- ブラウザ検出は "languageOnly"（例: 'es-419' → 'es'）で正規化。
- フォールバックはフロント/DBともに 'en' で統一。
- DBの CHECK 制約は「許可リスト方式」。追加時にマイグレーションで許可コードを加える。
- サインアップ時メタ言語は DB 側でホワイトリスト検証（未許可 → 'en'）。

## 追加手順（標準フロー）

ここでは例として『ko, zh, es』を追加する手順を示します（他言語も同様）。

### 1) 仕様確定（承認事項）
- 追加言語コード: ['ko','zh','es']
- 既定フォールバック: 'en'
- リージョンの扱い: 一旦使用しない（必要時のみ 'pt-BR' 等を個別追加）

### 2) フロントエンドの変更
- `src/i18n/locales/` に各言語ファイルを追加
  - `ko.json`, `zh.json`, `es.json`
  - 初期は `en.json` をコピー（未訳箇所は英語のまま）。
- `src/i18n/index.ts`
  - import 追加: `import ko from './locales/ko.json'` 等。
  - `resources` に `ko/zh/es` を追加。
  - `supportedLngs` に `['en','ja','ko','zh','es']` を設定。
  - `detection` の見直し：
    - `convertDetectedLanguage` は "ja以外はen" という現状を廃止。
    - 代わりに、言語コードを `split('-')[0]` で正規化し、`supportedLngs` に含まれる場合のみ採用。
    - 未対応は `fallbackLng`（'en'）へ。
- `src/lib/utils.ts`
  - `detectBrowserLanguage()` の `supportedLanguages` を `['en','ja','ko','zh','es']` に拡張。
  - `validateLanguageCode()` の `supportedLanguages` も同様に拡張。
  - フォールバック整合性を 'en' に統一。

> 補足: i18next の LanguageDetector に任せる設計でも良いですが、アプリ側ユーティリティの `detectBrowserLanguage` も他所で利用されているため、両者を同じ許可リストで整えるのが安全です。

### 3) データベースの変更（マイグレーション）
- 目的:
  - `profiles.language` の CHECK 制約に 'ko','zh','es' を追加。
  - 既定値（DEFAULT）を 'en' に統一（仕様書/実運用に合わせて）。
  - `handle_new_user()` でメタ言語を安全に保存する（email カラムに依存しない）。

- マイグレーション（雛形）
  - ファイル名例: `supabase/migrations/20250809000000_extend_profiles_language_and_fix_handle_new_user.sql`
  - 主要内容（ダイジェスト）:
    1. 既存制約の見直し（存在確認→DROP→CREATE で上書き）。
    2. DEFAULT 'en' を設定。
    3. 既存データで未許可値/NULL があれば 'en' に修正。
    4. `handle_new_user()` を email 非依存にし、メタ言語をホワイトリストで採用：
       - 許可: ('en','ja','ko','zh','es')
       - メタ未設定/未許可 → 'en'
       - INSERT 時に `language` を必ず明示保存。

- 運用:
  - 先に「開発環境 `wdttluticnlqzmqmfvgt`」に適用→検証→問題なければ「本番 `qgqcjtjxaoplhxurbpis`」へ。
  - 既存 `handle_new_user()` が email カラムを参照していないか、事前に確認/修正。

### 4) QA / 検証
- ブラウザ言語=ko で未ログイン閲覧: ko UI になる（なければ 'en'）。
- 新規サインアップ（ブラウザ=ko）: `profiles.language = 'ko'` で作成される。
- 既存ユーザー: DB `profiles.language` を優先して UI が変わる。
- 未対応言語（例: fr）: 'en' で表示。
- i18nキー欠落: 英語にフォールバック（i18nextのfallback機能）。
- リグレッション: ja/en が従来通りに動作。

### 5) ロールアウト
- PR: 上記フロント/DBの変更をまとめてレビュー。
- マイグレーション: 開発→本番の順に適用。適用ログを `.cursor/docs/dev-rules/YYYY-MM-DD_多言語拡張.mdc` に記録。
- 翻訳運用: 初回は英語コピーのまま公開→順次人手校正。

## 推奨コード変更（参考）

以下は実装時に変更すべきポイントの参考（抜粋）。実装の際は実ファイルに合わせて微調整してください。

### i18n 初期化（`src/i18n/index.ts` の方向性）
- `supportedLngs`: `['en','ja','ko','zh','es']`
- `detection`:
  - `order: ['localStorage','navigator','htmlTag']`
  - `convertDetectedLanguage`: 
    - 入力を小文字化→`split('-')[0]` で正規化。
    - 許可リストに含まれれば採用、なければ 'en'。

### 言語ユーティリティ（`src/lib/utils.ts` の方向性）
- `detectBrowserLanguage()` / `validateLanguageCode()` の許可リストを共通化。
- フォールバックは 'en' に統一。

### DB マイグレーション（SQLの方向性）
- CHECK 制約の再作成例:
  - `ALTER TABLE public.profiles DROP CONSTRAINT IF EXISTS profiles_language_check;`
  - `ALTER TABLE public.profiles ADD CONSTRAINT profiles_language_check CHECK (language IN ('en','ja','ko','zh','es'));`
- DEFAULT 設定:
  - `ALTER TABLE public.profiles ALTER COLUMN language SET DEFAULT 'en';`
- 既存値のクリーンアップ:
  - `UPDATE public.profiles SET language = 'en' WHERE language IS NULL OR language NOT IN ('en','ja','ko','zh','es');`
- `handle_new_user()` 修正版のポイント:
  - email カラムを参照しない。
  - `detected_language := 'en'` で初期化。
  - `IF NEW.raw_user_meta_data ? 'language' THEN ...` で取得→ホワイトリスト判定。
  - `INSERT INTO public.profiles (id, username, language, created_at, updated_at) VALUES (...)`。

## 既知の課題と注意
- レポジトリ上の `handle_new_user()` 実装が複数存在し、`email` カラム削除後の更新が不完全な履歴がある。
  - 追加言語適用前に、現行DBの `handle_new_user()` が最新仕様（email非依存・言語保存あり）であることを必ず確認。
- `utils.ts` のフォールバック不一致（detect=en, validate=ja）は統一が必要。
- RTL言語（ar 等）を追加する場合は、UI/スタイル対応（dir='rtl'）を別タスクで設計する。
